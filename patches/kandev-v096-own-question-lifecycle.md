## Contract

`get_own_question_status_kandev` accepts:

```json
{"question_ids":["coordinator_visibility_scope_20261012_1"]}
```

The MCP server injects its own task/session IDs. The backend compares these to
trusted MCP provenance and verifies the task's live workspace, nonarchive status,
and the session's exact task ownership and nonterminal state. Unknown identities,
foreign or peer targets, caller mismatch, automation, and inactive callers fail
closed. No task/session/workspace target is exposed in the callable schema.
The tool is registered alongside the existing user-question capability; external
and automation catalogs receive no new authority.

Response:

```json
{
  "task_id":"<authenticated own task>",
  "session_id":"<authenticated own active session>",
  "pending_id":"<original durable bundle identity when present>",
  "status":"pending",
  "retry_allowed":false,
  "questions":[{
    "question_id":"<requested exact ID>",
    "message_id":"<durable clarification identity>",
    "requesting_turn_id":"<original turn>",
    "status":"pending",
    "created_at":"<RFC3339 timestamp>",
    "updated_at":"<RFC3339 timestamp>",
    "agent_disconnected":true,
    "question_sha256":"<nonsecret identity digest>"
  }]
}
```

For answered questions, the question item includes the recorded `answer` with
`question_id`, `selected_options`, and/or `custom_text`. It reads only answers
embedded in that caller's own agent-authored clarification record. It never
loads conversation content, Human-message bodies, another session's records,
peer questions, or foreign workspace data. At most four IDs, sixteen candidate
records, and 64 KiB of metadata per record are accepted. Duplicate IDs, multiple
matching bundles, incomplete identity sets, corrupt or oversized records fail
closed rather than guessing or returning a partial answer.

| Status | Meaning | Retry |
| --- | --- | --- |
| `not_created` | No durable agent-authored clarification record exists for the exact requested IDs in this caller's task/session. This does not prove that an earlier transport was never attempted. | Allowed with the same stable IDs and `return_mode: receipt`. |
| `pending` | At least one requested question remains pending. A disconnected waiter does not answer or reject it. | No recreation. End the turn; read again after legitimate Human input. |
| `answered` | Requested questions have recorded answers. | No recreation; retain identity and consume the recorded answers normally. |
| `rejected` | A requested question records a Human rejection. | No recreation or scope grant. |
| `expired` / `cancelled` | Existing lifecycle records are terminal. | No automatic recreation. |
| `unknown` | Lifecycle/answer data is incomplete or unrecognized. | No retry or inferred answer. |

`status` describes the requested exact questions; it is not an assertion that
all other questions in a larger bundle are answered, or that an old requesting
turn is still eligible for the operational Inbox. No history/visibility policy,
routine, queue, response, acknowledgement, or permission mutation is added.

## Reliable ask return and deduplication

The existing `ask_user_question_kandev` adds optional
`"return_mode":"receipt"`. This requires explicit stable question IDs,
publishes through the existing clarification message creator and event path,
and returns the durable receipt immediately. It does not wait for Human input
inside `tools/call` and does not create an unwaited in-memory response entry.
Human answers use the existing durable resolution/resume fallback.

Before creation, the backend serializes exact durable correlation with
publication. An identical retry returns the original identity and recorded
lifecycle/answers. Changed question content or context under a stable identity,
partial/colliding identities, and failed publication reject without discarding
old data. Creation failure requires status correlation before any retry.
After restart, correlation uses persistent clarification rows rather than an
in-memory deduplication cache. The deployment has one backend owner; no new
cross-process/distributed writer contract is introduced.

The normal blocking ask remains available. Custom stable IDs also correlate
before a blocking retry. Legacy autogenerated `q1`/`q2` identifiers retain their
existing interaction-local behavior; use explicit IDs and receipt mode for the
durable contract. A pending receipt is never an answer or approval. Existing
hard Human-input barrier instructions still require ending the turn.
