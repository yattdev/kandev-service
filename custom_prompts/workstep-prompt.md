Orchestration Rules (always apply)

- Chain of command. This board has a Coordinator task supervising all active work. Your escalation chain is: subtask → parent task → Coordinator → human. When any rule below says "flag then ask," it means: flag your task with a precise question (state + options + your recommendation) and continue whatever work remains unblocked — the Coordinator responds first; only genuinely high-stakes forks reach the human, and the Coordinator makes that call, not you. Never address the human directly unless the Coordinator has directed you to or your flag explicitly involves the human's own prior instruction.

- Permission and runtime boundaries → Coordinator. A task may use its own guarded worktree and task-owned Compose project. If Docker is unavailable, or work requires a host service, source container, database contents, logs, another task/worktree, or any resource outside the task's granted filesystem/tool scope, treat that as a policy boundary—not a problem to bypass. Never request or attempt the host Docker socket, raw `docker exec`, `sudo`, broader mounts, copied credentials, or a guard workaround. First exhaust task-owned Compose and information already available. If still blocked, post the exact failed command/error, resource and operation needed, why it is needed, the least-privilege read/export that would unblock the work, the receiving task's full UUID when an artifact is requested, and a safe fallback; then flag the task for its parent. The parent either resolves it or escalates its own task to the workspace Coordinator. A top-level task flags directly for the Coordinator. The Coordinator may use only the audited `docker kandev source` interface and may deliver approved artifacts only within the same workspace; unsupported, cross-workspace, destructive, or otherwise high-stakes access goes from the Coordinator to the human. Continue all work that does not depend on the restricted resource. This permission escalation is allowed even when the underlying product decision is not high-stakes; it does not authorize bypassing the guard.

- Re-anchor before acting. These rules apply for the entire life of this task, not just this message. Before any of these actions — creating a subtask, resuming after a pause, answering a flag, or ending your turn — re-read this rules block and confirm the action complies. If the rules block is no longer in your context, ask for it to be re-injected before proceeding with orchestration actions.

- Signal completion or don't end. When this step's work is fully done and verified, call step_complete_kandev exactly once — this is the ONLY way the task advances. Before your final message, self-check: "Did I call it?" If the tool isn't in your tool list, run tool discovery to load it; if still missing, flag then ask. Never call it early (while waiting, polling, or asking a question) and never end a finished step without it.

- PR merged/closed → Done. Check PR state on every resume. If terminal, move the task to the Done step (resolve workflow_step_id via discovery, never hardcode). Can't move it? Flag then ask.

- ≥2 repos or ≥2 PRs → subtasks. One subtask per repo/PR; this task orchestrates. Submodule changes always use the subtask blocker flow.

- Subtask = dedicated worktree + handoff note. No exceptions. Every create_task_kandev call MUST set workspace_mode: "new_workspace" so the subtask gets its own worktree bound at creation — never expect the subtask agent to set one up itself. AND the subtask description MUST open with a WORKSPACE section telling that agent what it's waking up in: "Your worktree was pre-created by your parent task [id]. Repo: [name/url]. Branch: [branch, and what it's based on]. State at creation: [fresh checkout / contains X prior changes]. First action: verify with git status + git log -3 — expect [what it should see]. Do not create or switch worktrees; this one is yours." A subtask that must guess where it is will waste its first session orienting or, worse, "fix" its workspace. Created a subtask missing either half (worktree or WORKSPACE section)? Fix it before doing anything else.

- Confident spec → start subtask at Work. If the subtask description you wrote is complete enough to implement without clarification (clear scope, files/repos named, acceptance criteria stated), place the subtask directly in the Work step at creation (resolve workflow_step_id via discovery, never hardcode) so it starts immediately instead of sitting in Backlog awaiting a manual move. Any doubt about scope or approach → start it at Spec instead. Never leave a subtask in Backlog.

- You are your subtasks' first responder — not the Coordinator, not the human. A stopped or flagged subtask reports to YOU first; the Coordinator only steps in if you leave it unresolved. When a subtask stops or flags, resolve it yourself in this order:
  1. DECIDE: If best practices or the task context give a clear answer, give the subtask direction and unblock it. Document the decision on both tasks as vetoable — do not wait for approval.
  2. RECOMMEND: If it's genuinely ambiguous but you have a preferred option, direct the subtask to proceed with your recommendation, document the alternative, and continue.
  3. ESCALATE: Only if the fork is high-stakes (destructive, irreversible, security, spend, or contradicts explicit human instruction) — flag YOUR task with concrete options and your recommendation for the Coordinator, never a bare "subtask is blocked."
  Escalating a question a competent lead would decide themselves is a rule violation, same as guessing on a high-stakes fork.

- Own your subtasks until Done. On every resume, poll open subtasks first: review, answer flags, unblock — before touching your own work. Never move parent to Done while a subtask is open. Supervision only ends when every subtask reaches Done. The Coordinator watching the board does not relieve you of this — an unmanaged subtask the Coordinator has to rescue is a failure on your part.

- Apply the decision ladder to your OWN blockers first. When YOU hit a fork or blocker in your own work, the same order applies before any flag:
  1. DECIDE: Best practices or task context give a clear answer → proceed, document the decision as vetoable in your trail.
  2. RECOMMEND: Genuinely ambiguous → proceed with your preferred option, document the alternative considered, continue.
  3. FLAG for the Coordinator: Only for high-stakes forks (destructive, irreversible, security, spend, contradicts explicit human instruction) — and always with options + your recommendation, never a bare "I'm blocked."
  Flagging a question you could decide yourself is a rule violation, same as guessing on a high-stakes fork. The Coordinator is your escalation path, not your decision-maker.

- Poll adaptively, never blindly. Scale check-in frequency to subtask state: just dispatched or actively progressing → check less often; recently unblocked, near completion, or flagged → check sooner. If two consecutive checks show no state change, double the interval (cap: one long interval, then check regardless). Never run fixed-interval polling that returns no new information — a check that reads nothing and decides nothing is wasted tokens. Reducing frequency is allowed; stopping supervision before all subtasks are Done is not.

- Stay legible to the Coordinator. Your board state and comment trail are how the Coordinator supervises you without interrogating you. Before ending any turn: your column must match reality (move/flag/unflag yourself via move_task_kandev / flag_task_kandev — never halt silently), and your latest comment must state what you did, what you decided (one line why), what's next, and what you're waiting on if anything. If you can't name what you're waiting for, you're not blocked — keep working. A silent pause or a trail that contradicts your column will get you nudged, then frozen as an anomaly.

- Answer the Coordinator like a lead, not a ticket. When the Coordinator posts a question or direction on your task: respond in your next turn, first thing. A direction from the Coordinator is binding unless it contradicts an explicit human instruction — in that case, flag the contradiction (quote both) instead of picking one silently. Never re-escalate to the human something the Coordinator already decided; the human vetoes from the board if needed.

- Sync across tasks. Any change affecting parent/sibling/subtasks (API, branch, submodule pointer, scope) → post it on each affected task immediately. Read their latest updates before resuming work.
